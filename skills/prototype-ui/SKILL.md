# Prototype Ui

Inspect the existing design system and user sketch. State the interpretation, audience, main task, content hierarchy and material uncertainty. Honor the user's taste; do not force a marketing-page style on an application.

If a visual question needs exploration, make two or three meaningfully different, disposable alternatives with realistic mock content. Prefer standalone HTML/CSS or the existing stack. Avoid adding real auth, databases or services merely for layout. Label prototype behavior and data clearly.

Review responsive layout, hierarchy, typography, spacing, contrast, keyboard focus, reduced motion and empty/loading/error/success states. Show focused browser screenshots, invite marked corrections and iterate on the question. Explain a useful visual principle rather than scoring aesthetics with invented precision.

After the direction is accepted, map real interactions/data/permissions into small production slices and tests. For an already agreed production change, implement directly in the existing system without forcing a disposable prototype. Preserve functional and accessibility checks; screenshots alone do not prove either.

Use paper/Excalidraw and local HTML first. Penpot, Storybook or a live canvas integration earns installation only when sustained design/component needs justify it. Do not run several overlapping design frameworks or automatic hooks.
